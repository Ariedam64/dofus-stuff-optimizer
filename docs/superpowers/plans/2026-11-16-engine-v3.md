# Engine v3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Better stuffs, a tighter proven gap and faster searches. The approach: bound tightening, weapon decomposition, critical bands and LNS (part 1), plus a persistent worker pool and parallelism (part 2). The exact evaluator and the output contract stay unchanged.

**Architecture:**

- A persistent `SolverWorkerPool` (preloaded GameData) runs sub-searches in parallel.
- `SolverSession` partitions the search by weapon groups. Stuffs with different weapons are always diverse, so the merged top-N stays exact. It prunes partitions by bound.
- Inside `StuffSolver`, three layers improve the model and the search:
    - tightened variable bounds (`BoundTightener`);
    - critical bands;
    - an LNS improvement loop.

**Tech Stack:** Node 24 CommonJS, `highs` (already installed), `worker_threads`, `os.availableParallelism()`. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-16-engine-v3-design.md`

## Global Constraints

- **Unchanged:** the exact damage evaluator (`StuffEvaluator`, `TurnPlanner`, `DamageCalculator`) and the result/page/agent contracts.
- **Soundness:** every new bound must stay a VALID upper bound. A stuff is `solverStatus: "optimal"` only with a valid proof. When in doubt, degrade the status.
- **Pool size:** at most `min(os.availableParallelism() − 1, config.MAX_SOLVER_WORKERS)` workers; `MAX_SOLVER_WORKERS = 4`.
- **Conventions:** follow the author's conventions (one class per file, `#private`, constants at the top, no magic numbers, files ≤ ~300 lines, English code, French UI).
- **Git:** NO git commits, NO git add. Parallel tasks edit only their listed files.
- **Benchmark:** `npm run bench` must not regress against the v2 baseline (best score per query ≥ baseline − 0.5 %, total time ≤ baseline).

### Task 1: Persistent worker pool

**Files:**

- create `src/optimizer/SolverWorkerPool.js`;
- modify `src/optimizer/SolverWorkerClient.js`, `src/solver/SolverWorker.js`, `src/optimizer/OptimizationManager.js`, `src/web/WebServer.js`, `src/cli/CommandLine.js`, `src/config.js`;
- tests under `tests/optimizer/`.

**Interfaces:**

- `class SolverWorkerPool` exposes `constructor({ config, size })`, `async start()` (spawns the workers, each loading GameData once and posting READY), `run(job, { signal }) → AsyncIterable<message>` (queues when all workers are busy), and `async close()`.
- **Job:** `{ queryJson, warmStartIds, weaponIds?: number[] | null }`. `weaponIds` restricts the weapon slot to those ids; `null` means all; `[]` means no weapon.
- **Abort:** an aborted job terminates that worker and spawns a fresh, preloaded replacement.
- `OptimizationManager` owns the pool: it creates it lazily, and `close()` is called by WebServer `stop()` and at the end of the CLI.
- The in-process runner stays available for tests.

**Tests:**

- a second search reuses warm workers: no GameData reload, so the time to the first message drops;
- abort replaces the worker;
- concurrent jobs run in parallel up to the pool size;
- `close` terminates all workers.

### Task 2: Bound tightening

**Files:**

- create `src/solver/BoundTightener.js`;
- modify `src/solver/StatBounds.js`, `src/solver/MilpModelBuilder.js` (and the damage models only where they consume bounds);
- tests `tests/solver/BoundTightener.test.js`.

**Behaviour:**

- Before the exact phase, compute for every characteristic the model uses (element stat incl. points, power, damage, element damage, critical, critical damage, % factors, AP, MP) a valid [min, max]. The values must account for:
    - slot capacities;
    - set bonuses;
    - points;
    - scrolls;
    - exos;
    - query minimums;
    - the 12/6 caps.
- Method: per-slot best contributions are cheap, and short LP solves maximizing/minimizing each stat over the LP relaxation are tighter (time-boxed; the cheap bound is the fallback).
- Use the tightened bounds for variable bounds, McCormick envelopes and big-M constants.

**Tests:**

- property: on seeded fixtures, every tightened [min, max] contains the brute-force min/max over all valid stuffs;
- the brute-force optimum is unchanged;
- on the real Crâ query, report the LP-relaxation bound before/after.

### Task 3: Critical bands

**Files:** `src/solver/ExpectedDamageModel.js`, `src/solver/DamageModel.js`, `src/solver/StuffSolver.js` (band orchestration), tests.

**Behaviour:**

- Split the critical chance into bands that cover [0, 100] %: config `CRITICAL_BANDS`, e.g. `[[0, 0.25], [0.25, 0.5], [0.5, 0.75], [0.75, 1]]`. Within a band the expected-damage linearization is simpler/tighter.
- A stuff from band b is valid; the global optimum is the max over bands; the global proof needs every band either solved to optimality or bounded below the incumbent.
- Bands may run in parallel through the pool (job field `criticalBand`).
- Exactness: the model must still equal the evaluator at integer points inside each band.

**Tests:** brute-force cross-checks across seeds with varied crit; statuses stay honest.

### Task 4: Weapon decomposition

**Files:** `src/optimizer/SolverSession.js`, new `src/optimizer/WeaponPartitioner.js`, `src/optimizer/OptimizationManager.js` (only if needed), tests.

**Behaviour:**

- Partition the weapon candidates into groups: per weapon for the top ones by single-item contribution, then grouped; plus a "no weapon" group.
- Run one sub-search per group through the pool (Task 1 `weaponIds`), most promising first.
- Merge the stream:
    - stuffs with different weapons are always diverse (diversity rule), and each partition enforces diversity internally;
    - so the global top-N is exactly the best N of the union of the per-partition diverse lists, ranked by exact score.
- Prune: skip/stop a partition whose proven upper bound is ≤ the current N-th best exact score.
- `isOptimal`/`no-valid-stuff` semantics: proven only when every partition completed or was pruned by a valid bound.

**Tests:**

- merged results equal the single-search results on seeded fixtures (brute force);
- pruning never drops a better stuff;
- infeasible queries are still proven.

### Task 5: LNS improvement loop

**Files:** new `src/solver/NeighbourhoodSearch.js`, `src/solver/StuffSolver.js` (hook), tests.

**Behaviour:**

- From the incumbent, repeatedly fix all but k slots (k from config, e.g. 4, rotating slot subsets).
- Solve the small MILP within a short time slice and keep strict improvements (exact score).
- Run while the time budget remains and before the exact phase proves.
- Never claims optimality by itself.

**Tests:** LNS never returns a worse or invalid stuff; on seeded fixtures it reaches the brute-force optimum from a deliberately bad incumbent.
